# 写真測量サーベイグリッド設計 — 2026-10-21

## 1. 目的と背景

VTOL 機(ArduPilot QuadPlane)を**固定翼モードで**飛ばし、下向きに固定したソニーのカメラ(α7R IV + 35 mm)で、
ArduPilot の距離トリガ(`DO_SET_CAM_TRIGG_DIST`)によるインターバル撮影を行い、オルソを作る。
これまでは Mission Planner の Survey (Grid) で計画していた。

ユーザーが現場で不安だったのは次の 4 点:

1. 本当に撮影されているか
2. 旋回中の傾いた写真が混ざらないか
3. 速すぎてブレていないか
4. EXIF に GPS 情報が入るか

このうち 2 と 3 は**飛ぶ前の計画で防げる**ので、今回の対象にする。
1(飛行中・飛行後の撮影確認)と 4(ジオタグ付け)は後回し(§2 非ゴール)。

作るもの: 解像度・高度・オーバーラップ・旋回パターン・ラインの方角・速度などを変えながら、
撮影ミッションを**ライブで確認・編集し、最後に機体へ書く WP 列まで確認できる**計画画面。
使いやすさを作り込む。

## 2. ゴール / 非ゴール / アンチゴール

**ゴール**
- 今のミッション作成画面に「サーベイ」項目を足す(ユーザー決定: 案 A)。
  - 撮影条件ごと保存し、後日でも条件を変えて作り直せる。
- 撮影範囲は、地図上で多角形を描くか、KML を読み込む(両方。ユーザー決定)。
- 条件を変えるたびに、地図(2D/3D)の撮影ライン・旋回・数値がその場で更新される。
- 生成された WP を、機体に書く番号どおりに一覧・地図・3D で確認できる。
- 固定翼の旋回を地図どおりに飛ばせる(円弧を WP で分割)。ライン飛ばし(n 本)ができる。
- 撮影は直線区間だけで行う。旋回中・助走中は撮影しない。
- ブレと、最悪地点の解像度・オーバーラップが計画時に分かる。

**非ゴール(今回やらない)**
- 飛行中・飛行後の撮影確認(撮影点の表示、抜けの検出)と、ジオタグ付け(ユーザー: 後で)。
- VTOL をコプター状態で使う測量(ユーザー: 使わない)。
- 地形追従の高度(ユーザー: 一定高度で飛びたい)。
- Mission Planner にあるが今回不要と判断したもの(私の判断、§8):
  - 回廊(コリドー)、スパイラル、ミッション分割
  - `DO_DIGICAM_CONTROL` / サーボによるトリガ
  - コプター向けの機首保持・WP 待機・スプライン

**アンチゴール(これになったら失敗)**
- 地図に描いた旋回と、機体が実際に飛ぶ軌道が大きく違う。
- 旋回中や助走中に撮影が入る。
- 条件をいじるたびに画面が固まる、または待たされる。
- 生成した WP が機体に書かれる内容と食い違う(一覧の見た目と、書込・検証・比較表の距離が別物になる)。

## 3. 制約

- 既存のルールは**すべて**守る:
  - デザイン(`prototype.css` を手で直さない、Lucide アイコンのみ)
  - 状態は immutable、ファイル ≤ 400 行目安・最大 800 行、関数 < 50 行
  - TDD、prettier を使わない
- 機体へ書くのは普通の MAVLink ミッション項目だけ。サーベイはアプリ内の概念で、機体は知らない。
- 既存の書込・検証・統計・ブリーフィング・`.waypoints` 書き出しは、展開後の WP 列でそのまま動くこと。
- Plane / QuadPlane は `NAV_ARC_WAYPOINT`(36)を実行しない。
  - upstream master(2026-10-20)とユーザーのフォークの両方で、Plane に処理コードが無いことを確認した。

## 5. 振る舞いの詳細

### 5.1 サーベイ項目の追加
- コマンドパレット(「コマンドを挿入」)に「サーベイ」を加える。選ぶと、地図で多角形を描くモードに入る。
- 同じ場所から「KML を読み込む」も選べる。
  - KML の `Polygon` を読む。複数あれば選ばせる。
  - 外周だけを使い、穴(innerBoundary)は無視して、無視したことを知らせる。
- 一覧ではサーベイは 1 行で表示する。例: `▸ サーベイ 北区画 · 58 WP · 1,240 枚`。
  - 前後に離陸・RTL・普通の WP などを自由に置ける。1 つのミッションに複数のサーベイを置ける。
- 行を展開すると、生成された項目が**機体に書く番号どおり**に並ぶ(読み取り専用、薄い表示)。
  - 撮影開始・停止のコマンド、旋回の分割 WP も含む。
  - 1 行を選ぶと、地図と 3D でその点を示す。

### 5.2 右パネル(サーベイを選んだとき)
上から次の順に並べる。各値はすぐに反映する。

- **カメラ:** 一覧から選ぶ。センサー幅×高さ(mm)、画素数(横×縦)、焦点距離(mm)、シャッター速度、最短撮影間隔(s)を表示・変更でき、「新しいカメラとして保存」もできる。
  - カメラの向き(長辺を進行方向に対して横 / 縦)も選べる。Mission Planner の `CHK_camdirection` に相当。
- **解像度(cm/px)と高度(m):** どちらかを入れると、もう片方が決まる。
- **オーバーラップ:** 前後(%)、左右(%)。
- **ラインの方角(°):** 地図上の回転ハンドルでも変えられる。既定は多角形の最も長い辺に平行。
- **開始位置:** 多角形の 4 隅、またはホームに近い隅。
- **速度(m/s):** 飛行速度(対気速度)。
- **想定風速(m/s):** 既定 0。最悪値の計算に使う。
- **範囲外の余白(m):** 既定はフットプリントの半分。
- **ライン飛ばし(本)と旋回:**
  - 旋回の作り方は「WP 分割」か「ArcWaypoint」を選ぶ。
  - 旋回のバンク角(°)を指定できる。
- **助走・行き過ぎ(m):** 撮影区間の前後に足す直線。自動計算値を初期値にし、手で上書きもできる。
- **数値表示:**
  - 写真枚数、撮影距離(m)と撮影間隔(s)
  - ブレ(cm と px)
  - 地上フットプリント、面積、ライン数、旋回半径
  - 総距離と推定時間
  - 範囲内の地表の最高・最低標高と、そこでの解像度・前後/左右オーバーラップ(最悪値を強調)
- **注意(色で示すだけで、書込は止めない):**
  - ブレが 1 px を超える
  - 撮影間隔がカメラの最短撮影間隔を下回る
  - ライン飛ばしが旋回直径に足りない
  - 最悪地点のオーバーラップが設定より大きく下がる
  - ArcWaypoint を選んでいる
  - 予測軌道が撮影区間に入るまでに直線に乗り切れていない(§5.4)
- **「ウェイポイントに展開」:** §4 の決定どおり。

### 5.3 ルートの作り方
- **ライン:**
  - 方角に平行な線を、左右オーバーラップから出したライン間隔で並べ、多角形を余白の分だけ外へ広げた形で切り取る。
  - 凹多角形で 1 本が複数区間に分かれる場合は、別ラインとして扱う。
- **撮影点:** 前後オーバーラップから撮影距離を出す。
- **ラインの順番:**
  - ライン飛ばし n 本のとき、隣接ではなく n+1 本先へ移る。
  - 飛ばしたラインは、後の往復で埋める(Mission Planner の `minLaneSeparation` と同じ考え方)。
  - 旋回直径 > (n+1)×ライン間隔 のときは、足りる n を提案する。
- **1 本のラインの構成:**
  1. 助走の開始点(WP)
  2. 撮影開始点(余白を足した縁)に `DO_SET_CAM_TRIGG_DIST(撮影距離)`
  3. 撮影終了点(余白を足した縁)に `DO_SET_CAM_TRIGG_DIST(0)`
  4. 行き過ぎの終点(WP)
  5. 旋回
  - 撮影開始・終了の位置に WP を置き、その直後にトリガのコマンドを置く。
- **旋回:**
  - 半径は R = v² / (g·tan(バンク角)) で求める。v は最悪の対地速度(対気速度 + 想定風速)。
  - 「WP 分割」では、円弧を等角度で WP に分割する。分割の細かさはビルダーに任せる(§7)。
  - 「ArcWaypoint」では、円弧の終点に `NAV_ARC_WAYPOINT`(param1 = 弧の角度、時計回りが +)を置く。既存の 36 の扱いと同じ。
- **旋回の形(私の判断、§8-13):** 次の撮影ラインまでの横方向の距離 d と直径 2R を比べる。
  - d ≥ 2R: 1/4 円弧 + 直線 + 1/4 円弧(d = 2R なら半円)。
  - d < 2R: 外側にふくらむ Ω 形(膨らみ→戻り)で、地図どおりに飛べる形を生成し、注意を出す。書込は止めない。
- **速度:** サーベイの頭に `DO_CHANGE_SPEED`(対気速度)を置く。サーベイ後の速度の戻し方はビルダーに任せる(§7)。
- **高度:** 全点を REL(離陸地点基準)の一定高度にする。
- 生成は純粋関数(spec → 項目列)にする。同じ入力からは常に同じ出力。
  - 機体の種類(固定翼系 / コプター)、バンク角、`WP_RADIUS` は spec に**写し取って**持つ(私の判断、§8-14)。
  - 機体がつながっていればその値を初期値として写すが、後で機体が変わっても勝手に作り直さない。

### 5.4 地図表示
- **2D:**
  - 多角形(頂点をドラッグで編集)
  - 撮影区間(太線)、助走・旋回(細線)
  - 撮影点(ズームで出す)
  - 必要なら写真フットプリント(切り替え可)
- **3D:** 既存のミッション 3D 表示に、同じものを乗せる。
- **予測軌道:**
  - 既存の Plane 予測(`flightpath/planePath.ts`)を、展開後の WP に重ねる。
  - 機体の `WP_RADIUS` などで分割 WP が早めに切り上げられ、旋回が膨らむ・縮む場合に、それが見えるようにする。
  - 撮影開始点で予測軌道がラインからずれていれば注意を出す。
- 方角の回転ハンドル。

### 5.5 保存・既存機能との関係
- ミッションの保存・`.rgcsmission` には、サーベイの条件と多角形も入る。開き直すと再生成できる。
- 書込・検証・統計・ブリーフィングの比較・一括書込・`.waypoints` 書き出しは、展開後の WP 列を使う。`.waypoints` では、サーベイは普通の WP になる。
- 取り消し・やり直しは、条件の変更も 1 手として扱う。

## 6. データ(方向性。詳細はビルダー)
- `Mission.items` は今までどおり「機体に書く項目の平らな列」で、これが真実とする。
- サーベイは、これに**付箋を付ける**形で表す。私の判断、§8。
  - 例: `Mission.surveys: [{ id, first, count, spec }]`。`first..first+count` の範囲がそのサーベイの生成物。
  - `spec` には、多角形・カメラ値・撮影条件・旋回設定・助走/行き過ぎなどを入れる。
- 再生成では、その範囲を置き換える。前後の項目の番号ずれ(DO_JUMP の参照先など)は、既存の `remapJumps` と同じ考え方で直す。
- 「展開」は付箋を外すだけにする。
- **作り直しのタイミング(私の判断、§8-15):**
  - 作り直すのは、条件か多角形を変えたときだけ。開き直しや読み込みでは作り直さず、保存された items をそのまま使う。
  - 付箋より前に項目を挿入・削除したら、`first` をずらす。
  - 範囲の中の項目を、削除・移動・貼り付けなど通常の編集で変えた場合は、付箋を外して普通の WP にし、その旨を知らせる(取り消しで戻せる)。
- **カメラ値(私の判断、§8-16):** spec には、カメラの id ではなく値の写しを持つ。カメラ一覧を後で直しても、既存のミッションは変わらない。
- カメラ一覧はサーバーに保存し、オペレーター間で共有する(私の判断、§8)。初期登録の α7R IV は消せない。
- 生成ロジックの置き場所:
  - UI(TS)に置くと、ライブ更新が速い。
  - 検証のため、サーバー側でも「付箋の範囲と spec が一致するか」を確かめる必要は**ない**。機体に書くのは items であり、items は既存の検証を通る。

## 7. ビルダーに任せること
- 円弧の分割角度。WP_RADIUS との兼ね合いで、予測軌道が地図に近くなるように決める。
- サーベイ後の速度の戻し方(次の `DO_CHANGE_SPEED` まで持ち越すか、元に戻すか)。
- ライン順の具体的なアルゴリズム(貪欲法でよい)と、凹多角形の扱いの詳細。
- 助走・行き過ぎの自動計算式(旋回半径と速度から、直線に乗り切る距離)。
- 数値の更新の間引き(ドラッグ中など)。
- 撮影点の位相合わせ。
  - 隣のラインと撮影位置を揃えるかどうか。距離トリガは、コマンドを実行した位置から数えるので、撮影開始点の置き方で揃えることになる。
- `.rgcsmission` の version をどう扱うか(フィールド追加だけで 1 のままにするか)。

## 8. 私(設計者)が決めた点 — ユーザーが読んで確認する
1. **トリガ方式:** 距離トリガだけにする。ライン毎に開始で `DO_SET_CAM_TRIGG_DIST(撮影距離)`、終了で `(0)`。
   - Mission Planner の「break trigger」と同じ。
   - デジカメ制御・サーボ方式は入れない。
2. **データの持ち方:** items を真実として、サーベイは範囲の付箋にする(§6)。
   - 既存の書込・統計・ブリーフィングを変えずに済む。
3. **カメラ一覧:** サーバーに保存し、オペレーター間で共有する。
4. **カメラの「最短撮影間隔(s)」:** 新しい欄として足す(既定 1.0 s)。撮影間隔がこれを下回ると注意する。
5. **ブレの注意:** 1 px を超えたら注意する(会話で示した値)。
6. **旋回のバンク角:** 既定は 30° で、変更できる。機体が接続されていれば `ROLL_LIMIT_DEG` を横に表示し、それを超える値には注意を出す。
7. **開始位置:** 4 隅とホームに近い隅だけにする。Mission Planner の「任意の点」は入れない。
8. **交差グリッド(90° 回した 2 回目):** 入れない。オルソ目的なので不要と判断した。必要ならオプションで後から足せる。
9. **予測軌道の表示と、ずれの注意(§5.4):** 入れる。「地図どおりに飛ぶか」を確かめる手段として。
10. **コプター機の場合:** 旋回なし(ライン端で直接次のラインへ)で生成し、旋回関連の項目は隠す。今回の主対象ではない。
11. **KML の範囲:** `Polygon` の外周だけを使う。KMZ・穴・線は対象外。
12. **「任意の点から開始」「コリドー」「スパイラル」「分割」:** 入れない(§2 非ゴール)。
13. **旋回の形:** §5.3。直径に足りないときも Ω 形で地図どおりに生成し、注意だけ出す。
14. **機体の値の持ち方:** 機体の種類・バンク角・`WP_RADIUS` を spec に写し取る。オフラインでも計画でき、同じ spec からは同じ WP が出る。
15. **作り直し:** 条件・多角形を変えたときだけ。範囲内を通常の編集で触ったら付箋を外す(§6)。
16. **カメラ一覧の権限と保存:** どのオペレーターでも追加・編集・削除できる。初期登録の α7R IV は編集・削除不可。新しいテーブルと API を作る。spec はカメラ値の写しを持つ。
