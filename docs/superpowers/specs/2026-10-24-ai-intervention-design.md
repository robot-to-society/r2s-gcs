# AI 緊急介入(実験機能)設計

- 版: 0.3(2026-10-24、複数取得元の総合判断と設定ページを追加)
- 状態: ユーザーと合意した方針。実装は AI チャット(`docs/superpowers/plans/2026-10-24-ai-chat.md`)の後

## 1. 目的

複数機(例: 4 機で建物点検)を同時に運用すると、人の判断と操作が異常に追いつかない。**AI の役目は、人のオペレーションを安全に最大限支えること。中心は異常の兆候をいち早く察知すること**。接続中の全機体のテレメトリを常時監視し、飛行場所の天気や宇宙天気(太陽フレア・地磁気嵐)などの外的要因も合わせて判断して知らせる。ユーザーが許可した場合だけ、AI が安全側の操作を代わりに行う。

最初の対象は **トイレットボウル**(コンパス異常で、位置保持中の機体が半径を広げながら円を描く)。現場ではこれまで「可能な限り手動モードに切り替えて、人間のパイロットが降ろす」で対処してきた。AI 介入もこの手順をなぞる。

## 2. 目標 / 目標外 / やってはいけないこと

- 目標
  - 接続中の全機体のテレメトリを常時監視し、異常の兆候を数秒で検知して、音と画面で該当機を示す
  - 外的要因(天気・宇宙天気など、§5.3)を取り込み、飛行前と飛行中のリスクとして示す
  - ユーザーが実験機能をオンにしたときだけ、事前に決めた安全側の操作を自動で行う
  - 判断・操作をすべて記録し、あとで再生・検証できる
  - 将来の「ローカル LLM を載せた FC(機上 AI)」と同じ方針・同じ判定ロジックで連携できる
- 目標外(この版)
  - 壁接近・機体間接近・電池・GPS 乱れの検知(枠組みは共通にし、順次追加)
  - 地上リスク区域を使った経路選択(§6 の優先順位の枠だけ用意)
- やってはいけないこと
  - LLM の出力で直接機体を操作する(判定は決め打ちのルール。LLM は説明・要約・提案のみ)
  - 実験機能オフの状態で AI が機体へ何かを送る
  - アーム・離陸・パラメータ変更・フェールセーフ解除・フェンス外への移動
  - 人の操作を上書きする(人の操作は常に AI に勝つ)

## 3. 実験機能のオン / オフと同意

- アプリ設定に「実験機能」区画を新設し、その中に「AI 緊急介入」を置く。既定オフ。
- オンにできるのは admin ロールだけ。オンにするとき、アプリ内ダイアログ(`window.confirm` は使わない)で次の 3 点を示し、それぞれ明示的に許可をもらう:
  1. **テレメトリの常時監視**: 接続中の全機体のテレメトリを AI が常時読み、判断に使う(機上・GCS 内で処理し、外部 LLM を使う設定ならその要約が外部へ送られることも明記)
  2. **外部データの取得**: 飛行場所の位置(概略)を天気・宇宙天気などの外部サービスへ送って情報を得る(§5.3)
  3. **自動操作のリスク**: L2 / L3 に設定した事象では AI が機体を操作すること
- 3 のみ未許可なら「監視と警告だけ」で動く(L2 / L3 は選べない)。1 は監視機能の前提なので必須。
- オン / オフ、事象ごとのレベル変更はすべて監査ログ(`target = 'ai_intervention'`)。
- オフのとき、AI ができるのは警告と提案(AI チャットの提案カード)だけ。

## 4. 権限レベル(事象ごとに設定)

| レベル | 動き |
|---|---|
| L0 | 無効 |
| L1 | 警告と提案のみ(既定) |
| L2 | 取り消し猶予つき実行(既定 5 s のカウントダウン。人が「取り消し」で中止) |
| L3 | 即時実行 |

L2 / L3 は実験機能オンのときだけ選べる。

## 5. トイレットボウル

### 5.1 検知(決め打ち、毎周期)

- 対象モード: 位置を保つモード(Copter: LOITER / POSHOLD / GUIDED 静止 / AUTO の WP 待機、QuadPlane: QLOITER / GUIDED のホバー)。
- 兆候 A(必須): 目標位置がほぼ固定(GUIDED の目標・AUTO の WP が変わっていない)なのに、直近 10 s の水平速度ベクトルの向きが一方向に回り続け、位置の軌跡に当てはめた円の半径が増えている。
- 兆候 B: 機首方位と対地進路のずれが継続して大きい。
- 兆候 C: `EKF_STATUS_REPORT` のコンパス分散(compass_variance)が閾値超え。
- 判定: A かつ(B または C)。閾値と時間窓は設定値(既定値は SITL と実機ログで決める)。
- 誤検知対策: 1 兆候だけでは発動しない。風による定常ドリフト(回転しない)は A に当たらない。

### 5.2 対処(トイレットボウル)

1. 知らせる: 該当機を強調、音、画面上部に「UAV-03 トイレットボウルの兆候 — 手動で引き継いでください」。AI チャットに要約。
2. レベル L2 / L3 のとき、位置保持を使わないモードへ切替:
   - Copter: ALT_HOLD
   - QuadPlane: QHOVER
   - 高度は維持し、渦の拡大は止まる。風で流れるので **パイロットの引き継ぎが前提**。
3. 引き継ぎの確認: `RC_CHANNELS` のスティック操作、または人の GCS 操作を検知したら「引き継ぎ済み」とし、AI は以後その機体に何もしない。
4. 一定時間(既定 20 s)引き継がれなくても、**それ以上は介入しない**(警告を続ける)。危険な状態での追加の自動操作は行わない(ユーザー決定 2026-10-24)。LAND も位置制御を使い、渦を巻きながら降りるおそれがあるため。
5. FC 側の備えを点検画面で促す(機体側のフェールセーフが主): `FS_EKF_ACTION`、`FS_EKF_THRESH`、EKF3 の GSF ヨーリセット(`EK3_GSF_*`)。

### 5.3 外的要因

監視対象は機体のテレメトリだけでなく、飛行場所の外的要因も含める。外部データは決め打ちのルールで閾値判定し、LLM はそれを組み合わせた説明・要約を担う。

| 要因 | 主な影響 | 取得元(案) | 判定の例 |
|---|---|---|---|
| 風・突風 | 姿勢の乱れ、電池消費、ビル風 | 気象 API(例: Open-Meteo、気象庁の予報) + 機体の推定風(`WIND`) | 地上・高度の風速 / 突風が機体の上限の 70% 超で警告 |
| 降水・気温 | 防水限界、電池性能(低温) | 気象 API | 降水確率・気温が機体設定の範囲外 |
| 宇宙天気(太陽フレア・地磁気嵐) | GNSS 測位の劣化、コンパスの乱れ(トイレットボウルの一因) | NOAA SWPC の Kp 指数・警報、NICT 宇宙天気予報 | Kp ≥ 5 で警告、Kp ≥ 7 で強い警告。同時にコンパス・GNSS の兆候の感度を上げる |
| 地磁気の地域特性 | 偏角・磁気異常 | 世界磁気モデル(WMM、機上でも計算可) | 機体の偏角設定との差 |
| GNSS の状況 | 衛星数・DOP の予測 | 機体の `GPS_RAW_INT` / 衛星配置予測 | 飛行時間帯の予測 DOP が悪い |
| 日没・明るさ | 目視・カメラ | 計算 | 日没までの残り時間 |

- 飛行前: 飛行場所と時間帯の外的リスクを一覧にして示す(ブリーフィング)。
- 飛行中: 一定間隔(例: 10 分)で更新し、悪化したら知らせる。機体側の兆候(例: コンパス分散の上昇)と外的要因(例: Kp の上昇)が重なったら、兆候の重みを上げる。
- 外部サービスに届かないとき(現場にインターネットが無いなど)は「外的要因: 取得できず」と明示し、機体テレメトリだけで監視を続ける。最後に取得した値と取得時刻を表示する。
- 外部へ送るのは飛行場所の概略座標(例: 0.01° に丸め)だけ。

### 5.4 取得元は複数、総合判断(ユーザー決定 2026-10-24)

1 つの取得元に頼らず、使える取得元をできるだけ多く使い、複数源の情報を総合して判断する。

取得元の候補(利用規約・更新間隔・キーの要否は実装時に各サービスで確認する):

| 分類 | 取得元 | 得られるもの | キー |
|---|---|---|---|
| 気象(予報) | Open-Meteo(複数の数値予報モデル。JMA モデルを含む) | 地上・上空の風・突風、気温、降水、雲 | 不要 |
| 気象(観測) | 気象庁 アメダス(防災情報の JSON) | 最寄り観測所の風・気温・降水の実測 | 不要 |
| 気象(ナウキャスト) | 気象庁 雷ナウキャスト・降水ナウキャスト | 1 時間先までの雷活動度・降水 | 不要 |
| 気象(商用、任意) | OpenWeatherMap など | 予報・警報 | 要 |
| 機体自身 | `WIND`、`SCALED_PRESSURE`、バッテリー温度など | その場の実測 | — |
| 宇宙天気 | NOAA SWPC(`services.swpc.noaa.gov`) | Kp 指数(実測・予報・1 分推定)、警報、Dst | 不要 |
| 宇宙天気 | NICT 宇宙天気予報 | 日本向けの予報・警報 | 不要 |
| 宇宙天気 | GFZ Potsdam / 京都大学 WDC | Kp・Dst の確定値 | 不要 |
| 地磁気 | 世界磁気モデル(WMM、内蔵計算) | 偏角・伏角・全磁力 | — |
| GNSS | 衛星軌道(CelesTrak の軌道要素)から内蔵計算 | 飛行時間帯の衛星数・DOP 予測 | 不要 |
| 天文 | 内蔵計算 | 日の出・日没・薄明 | — |

総合判断の規則(決め打ち。LLM は結果の説明を担う):

- **安全側を採る**: 同じ要素(例: 突風)で取得元の値が割れたら、危険側(大きい方)を採用して判定する。
- **実測を優先**: 機体の実測 > 近傍の地上観測 > ナウキャスト > 予報の順に重みを付ける。古い値は鮮度に応じて重みを下げる。
- **不一致を知らせる**: 取得元どうしの差が大きいときは「取得元で値が割れています」と、それぞれの値と出典を示す。
- **出典と時刻を常に表示**: 判定の根拠ごとに取得元名と取得時刻を出す。
- **欠けても止まらない**: 取得元の一部が使えなくても、残りで判定を続け、欠けていることを示す。全部使えなければ「外的要因: 取得できず」(§5.3)。
- **機体側の兆候と組み合わせる**: 外的要因はそれ単独で介入はしない(警告と提案まで)。機体側の兆候と重なったとき、その兆候の判定を早める・重みを上げる。

### 5.5 アプリ設定「外的要因データ」ページ

アプリ設定に専用ページを設け、取得元を管理する(admin のみ編集可、変更は監査ログ)。

- 取得元ごと: 有効 / 無効、API キー(必要なものだけ。保存は暗号化 or 設定ファイル側、画面には末尾のみ表示)、更新間隔、タイムアウト
- 状態表示: 最終取得時刻、成功 / 失敗とエラー内容、次回取得予定、「今すぐ取得」
- 判定閾値: 風・突風・降水・気温・Kp などの警告 / 強い警告の閾値(機体の種類ごとに既定値)
- 位置の丸め精度(既定 0.01°)と、外部送信の同意状態(§3 の 2)
- オフライン時の挙動の説明

## 6. 判断の優先順位(全事象共通の枠)

候補動作ごとに予測経路と区域を照合し、上位ほど重いコストで比較する。

1. 人(作業員・通行人の区域)
2. 第三者の財産(隣の建物など)
3. 点検対象の建物(接触)
4. 他の機体
5. 自機
6. ミッション・点検データ

区域(人のいる区域 / 飛行禁止 / 建物の輪郭+安全距離 / 安全な着陸地点)は飛行前に地図で描く。トイレットボウルの対処(モード切替のみ)は経路を選ばないため、この版では記録と表示だけに使う。

## 7. 構成と機上 AI との連携

### 7.1 移植できる判定部

- 検知と方針は新しい純粋なクレート(例 `rgcs-guard`)に置く。入力 = 機体の時系列テレメトリ(位置・速度・姿勢・方位・EKF 状態・モード・目標)、出力 = 判定(事象・確度・根拠)と推奨動作。I/O・サーバー・非同期に依存しない。
- 同じクレートを、GCS(rgcs-server)と、将来の機上ノード / 機上 AI の両方で動かせるようにする(依存を最小にし、no_std 化の余地を残す)。
- 方針の設定(有効な事象・レベル・閾値・区域)は 1 つのデータ形式にし、GCS から機上へ配る(当面は RGCS の DB、将来は MAVLink FTP などで機上へ)。

### 7.2 GCS と機上 AI の役割分担

- 機上 AI があれば、機上を優先する(遅延が小さく、リンク断でも動く)。GCS 側は監視・表示・人への通知と、機上 AI が無い機体の代行。
- 二重操作を防ぐため、介入は「担当」を 1 つに決める: 機上 AI が介入したら機体からその旨を通知し(例: 専用コンポーネント ID の HEARTBEAT + STATUSTEXT、将来は専用メッセージ)、GCS はその機体への自動操作を止めて表示だけにする。
- 機上のローカル LLM も、判定は §5 の決め打ちルールが行い、LLM は状況説明・人への報告文・提案を担う(GCS の AI チャットと同じ役割分担)。

## 8. 記録と検証

- 判定ごとに: 入力の要約、各兆候の値、判定、選んだ動作、取り消し・引き継ぎの有無と時刻を記録し、飛行記録から再生できるようにする。
- SITL シナリオ: コンパスのオフセットや干渉を模擬するパラメータ(試験用 SITL のみで設定)でトイレットボウルを起こし、検知時間・誤検知・切替を確認する。風だけのドリフトで発動しないことも確認する。
- 実機の過去ログ(トイレットボウルが起きた飛行)があれば、それで閾値を決める。

## 9. 法的な前提

自動で操作しても、責任は操縦者に残る前提で設計する。レベル 3.5 / 4 の運用での扱いは別途確認する。
