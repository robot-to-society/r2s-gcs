# AI 緊急介入(実験機能)設計

- 版: 0.4(2026-10-26、v1 実装済み。計画 `docs/superpowers/plans/2026-10-25-ai-guard.md` の裁定 1–16 と既定値を反映)
- 版の履歴: 0.3(2026-10-24、複数取得元の総合判断と設定ページを追加)
- 状態: v1 実装済み(実験機能、既定オフ)。API は `docs/spec/50-api.md` §2.9 と §3.1、監査と安全規則は `docs/spec/70-safety-auth.md` §4.1、画面は `docs/spec/10-screens.md` §7、データは `docs/spec/60-data-model.md`

## 1. 目的

複数機(例: 4 機で建物点検)を同時に運用すると、人の判断と操作が異常に追いつかない。**AI の役目は、人のオペレーションを安全に最大限支えること。中心は異常の兆候をいち早く察知すること**。接続中の全機体のテレメトリを常時監視し、飛行場所の天気や宇宙天気(太陽フレア・地磁気嵐)などの外的要因も合わせて判断して知らせる。ユーザーが許可した場合だけ、AI が安全側の操作を代わりに行う。

最初の対象は **トイレットボウル**(コンパス異常で、位置保持中の機体が半径を広げながら円を描く)。現場ではこれまで「可能な限り手動モードに切り替えて、人間のパイロットが降ろす」で対処してきた。AI 介入もこの手順をなぞる。

## 2. 目標 / 目標外 / やってはいけないこと

- 目標
  - 接続中の全機体のテレメトリを常時監視し、異常の兆候を数秒で検知して、音と画面で該当機を示す
  - 外的要因(天気・宇宙天気など、§5.3)を取り込み、飛行前と飛行中のリスクとして示す
  - ユーザーが実験機能をオンにしたときだけ、事前に決めた安全側の操作を自動で行う
  - 判断・操作をすべて記録し、あとで再生・検証できる
  - 将来の「ローカル LLM を載せた FC(機上 AI)」と同じ方針・同じ判定ロジックで連携できる
- 目標外(この版)
  - 壁接近・機体間接近・電池・GPS 乱れの検知(枠組みは共通にし、順次追加)
  - 地上リスク区域を使った経路選択(§6 の優先順位の枠だけ用意)
- やってはいけないこと
  - LLM の出力で直接機体を操作する(判定は決め打ちのルール。LLM は説明・要約・提案のみ)
  - 実験機能オフの状態で AI が機体へ何かを送る
  - アーム・離陸・パラメータ変更・フェールセーフ解除・フェンス外への移動
  - 人の操作を上書きする(人の操作は常に AI に勝つ)

## 3. 実験機能のオン / オフと同意

- アプリ設定に「実験機能」区画を新設し、その中に「AI 緊急介入」を置く。既定オフ。
- オンにできるのは admin ロールだけ。オンにするとき、アプリ内ダイアログ(`window.confirm` は使わない)で次の 3 点を示し、それぞれ明示的に許可をもらう:
  1. **テレメトリの常時監視**: 接続中の全機体のテレメトリを AI が常時読み、判断に使う(機上・GCS 内で処理し、外部 LLM を使う設定ならその要約が外部へ送られることも明記)
  2. **外部データの取得**: 飛行場所の位置(概略)を天気・宇宙天気などの外部サービスへ送って情報を得る(§5.3)
  3. **自動操作のリスク**: L2 / L3 に設定した事象では AI が機体を操作すること
- 3 のみ未許可なら「監視と警告だけ」で動く(L2 / L3 は選べない)。1 は監視機能の前提なので必須。
- オン / オフ、事象ごとのレベル変更はすべて監査ログ(`target = 'ai_intervention'`)。
- オフのとき、AI ができるのは警告と提案(AI チャットの提案カード)だけ。
- v0.4 の決定(裁定 1):
  - **オフはオフ。** 無効のとき検知器は動かず、警告も出さず、外部取得も一切しない。日の出・日没と WMM は内蔵計算なので「外的要因データ」ページにだけ表示する。上の「警告と提案」は既存の AI チャットの提案のことを指す。
  - 同意 1 は有効化の必須条件。同意 2 が無ければ外部取得はすべて止める(位置を送らない SWPC も取得しない。同意 2 は外部送信全般を覆う)。同意 3 が無ければレベルは L1 が上限で、画面の L2 / L3 は押せない。
  - 無効にすると 3 つの同意はすべて消え、再度有効にするときはまた同意を求める。カウントダウン中に無効にするとそのカウントダウンは取り消し扱い(`cancelled`、by `disabled`)で、何も送らない。
  - 同意を変更(あとから 3 を許可する等)は有効のままできる。同意と変更は監査ログ(`enable` / `disable` / `set_level` / `set_guard_params`)。

## 4. 権限レベル(事象ごとに設定)

| レベル | 動き |
|---|---|
| L0 | 無効 |
| L1 | 警告と提案のみ(既定) |
| L2 | 取り消し猶予つき実行(既定 5 s のカウントダウン。人が「取り消し」で中止) |
| L3 | 即時実行 |

L2 / L3 は実験機能オンかつ同意 3 があるときだけ選べる。v1 の既定はトイレットボウル = L1。カウントダウンは 5 s(3〜15)、引き継ぎ待ちは 20 s(10〜120)。

## 5. トイレットボウル

### 5.1 検知(決め打ち、毎周期)

- 対象モード: 位置を保つモード(Copter: LOITER / POSHOLD / GUIDED 静止 / AUTO の WP 待機、QuadPlane: QLOITER / GUIDED のホバー)。
- 兆候 A(必須): 目標位置がほぼ固定(GUIDED の目標・AUTO の WP が変わっていない)なのに、直近 10 s の水平速度ベクトルの向きが一方向に回り続け、位置の軌跡に当てはめた円の半径が増えている。
- 兆候 B: 機首方位と対地進路のずれが継続して大きい。
- 兆候 C: `EKF_STATUS_REPORT` のコンパス分散(compass_variance)が閾値超え。
- 判定: A かつ(B または C)。閾値と時間窓は設定値(既定値は SITL と実機ログで決める)。
- 誤検知対策: 1 兆候だけでは発動しない。風による定常ドリフト(回転しない)は A に当たらない。

#### 5.1.1 v1 の既定値(裁定 2・3、`rgcs-guard` の `ToiletBowlConfig::default()`)

| 項目 | 既定値 |
|---|---|
| 入力 | `GLOBAL_POSITION_INT` 1 件ごとに 1 サンプル(10 Hz を要求)。窓 10 s、80 サンプル以上かつ 9 s 以上そろってから判定 |
| 対象モード | Copter: LOITER / POSHOLD / GUIDED(目標の移動 < 1.0 m)/ AUTO(窓の始まりで `wp_dist ≤ 3 m` かつミッション番号が変わらない =「WP 待機」の代わり)。QuadPlane: QLOITER と、`vtol_state = MC` の GUIDED。CIRCLE を含むそれ以外は対象外。対象外モードに出たら窓を捨てる |
| 目標固定 | GUIDED の目標が 1.0 m 以内、AUTO のミッション番号が不変、LOITER / POSHOLD / QLOITER は RC 受信中ならスティック ch1–4 が 1500 ± 40 µs |
| 兆候 A | 0.8 m/s 以上の区間で進路の変化の合計が \|Σ\| ≥ 270°、そのうち 0.8 以上の割合が Σ と同じ向き。窓の前半・後半それぞれに当てはめた円(Kåsa)の半径の増加が ≥ 0.05 m/s、最後の 1 s の平均半径 ≥ 1.5 m。最後の 1 s の半数以上がまだ 0.8 m/s 以上で動いている(回り続け) |
| 兆候 B | 0.8 m/s 以上のサンプルの 0.6 以上で \|機首方位 − 対地進路\| ≥ 45° |
| 兆候 C | 直近 2 s の `EKF_STATUS_REPORT.compass_variance` がすべて ≥ 0.5(2 件以上。Mission Planner の黄色と同じ値) |
| 判定 | A かつ(B または C)で「検知」。確度 A+B+C = 1.0、A+B / A+C = 0.7。A だけは「疑い」で記録のみ(警告しない)。15 s 検知が無ければ解消 |
| 外的要因 | Kp ≥ 5(警告)で `compass_var 0.4`・`min_turn_deg 225`、Kp ≥ 7(強い警告)で 0.3・180 に下げる。それ以外は変えない。Kp だけでは発動しない。管理者がより厳しい値を設定していれば、それを緩めない |

既定値は合成データの試験と試験用 SITL(§8.1)で確かめた。実機ログでの調整は §10 のとおり後日。
### 5.2 対処(トイレットボウル)

1. 知らせる: 該当機を強調、音、画面上部に「UAV-03 トイレットボウルの兆候 — 手動で引き継いでください」。AI チャットに要約。
2. レベル L2 / L3 のとき、位置保持を使わないモードへ切替:
   - Copter: ALT_HOLD
   - QuadPlane: QHOVER
   - 高度は維持し、渦の拡大は止まる。風で流れるので **パイロットの引き継ぎが前提**。
3. 引き継ぎの確認: `RC_CHANNELS` のスティック操作、または人の GCS 操作を検知したら「引き継ぎ済み」とし、AI は以後その機体に何もしない。
4. 一定時間(既定 20 s)引き継がれなくても、**それ以上は介入しない**(警告を続ける)。危険な状態での追加の自動操作は行わない(ユーザー決定 2026-10-24)。LAND も位置制御を使い、渦を巻きながら降りるおそれがあるため。
5. FC 側の備えを点検画面で促す(機体側のフェールセーフが主): `FS_EKF_ACTION`、`FS_EKF_THRESH`、EKF3 の GSF ヨーリセット(`EK3_GSF_*`)。

#### 5.2.1 v1 の決定(裁定 4〜7)

- **AI が送るのは `SetMode {ALT_HOLD | QHOVER}` だけ**(Copter → ALT_HOLD、`kind = plane` かつ VTOL の QuadPlane → QHOVER)。送る場所はサーバーの 1 か所(`guard_hub.rs` の `execute()`)だけで、操作者の `commands::command` を通らない(自分の切替を引き継ぎと取り違えない)。
- 送る直前(L2 はカウントダウン後)に次をすべて確認し直す: 有効かつ同意 3、L2(カウントダウン経過)または L3、直近 1 s 以内に「検知」、アーム中かつ対象モード、リンク正常(`commands::precheck`)、引き継ぎ無し、この飛行でまだ操作していない、取り消し無し。キューの結果が ok なら「実行済み」、失敗・タイムアウトなら「拒否」。どちらでも以後ディスアームまで手を出さない。
- 自動操作はアーム → ディスアームの間に 1 回まで。引き継ぎ・引き継ぎ無し(20 s)・取り消し・拒否のあとは、警告が解消して再検知しても何も送らない。
- 引き継ぎの判定: (a) RC ch1–4(`RCMAP_*` が取得済みならそれ)のどれかが、警告直前 1 s の中央値から 60 µs 以上を 300 ms 以上続けてずれた、(b) その機体への操作者のコマンド・Guided 目標が受理された、(c) AI が命じていないモード変更(パイロットの RC モードスイッチを含む)。`RC_CHANNELS` が 2 s 以上来ないときは「RC 未受信 — GCS 操作で引き継ぎ」と表示する。
- 取り消し: カウントダウン中ならログイン中の誰でも「取り消し」できる(`POST /api/guard/alerts/{id}/cancel`、監査)。その警告はこの飛行では操作しない。警告表示は解消か引き継ぎまで残る。
- 文言(固定): 検知「{機体名} トイレットボウルの兆候 — 手動で引き継いでください」、カウントダウン「{n} 秒後に {mode} へ切り替えます」、実行「{mode} に切り替えました — 風で流れます。手動で引き継いでください」、引き継ぎ「引き継ぎ済み」、引き継ぎ無し「引き継ぎが確認できません — AI はこれ以上操作しません」。
- 知らせ方: WS フレーム `guard_alert`(状態が変わるたび。カウントダウン中は 1 Hz で再送)、新しい画面向けに `GET /api/guard/alerts`。メッセージログ(source `system`、検知・引き継ぎ無しは error、実行・取り消しは warn、確認ボタンなし。バナーが確認の場)。地図マーカーと機体一覧は警告色で強調。音は画面側の Web Audio(880 Hz / 660 Hz 各 150 ms、10 s ごとに繰り返し、ブラウザごとにミュート可)。AI チャットにはローカルの警告項目を出す(LLM は呼ばない)。
### 5.3 外的要因

監視対象は機体のテレメトリだけでなく、飛行場所の外的要因も含める。外部データは決め打ちのルールで閾値判定し、LLM はそれを組み合わせた説明・要約を担う。

| 要因 | 主な影響 | 取得元(案) | 判定の例 |
|---|---|---|---|
| 風・突風 | 姿勢の乱れ、電池消費、ビル風 | 気象 API(例: Open-Meteo、気象庁の予報) + 機体の推定風(`WIND`) | 地上・高度の風速 / 突風が機体の上限の 70% 超で警告 |
| 降水・気温 | 防水限界、電池性能(低温) | 気象 API | 降水確率・気温が機体設定の範囲外 |
| 宇宙天気(太陽フレア・地磁気嵐) | GNSS 測位の劣化、コンパスの乱れ(トイレットボウルの一因) | NOAA SWPC の Kp 指数・警報、NICT 宇宙天気予報 | Kp ≥ 5 で警告、Kp ≥ 7 で強い警告。同時にコンパス・GNSS の兆候の感度を上げる |
| 地磁気の地域特性 | 偏角・磁気異常 | 世界磁気モデル(WMM、機上でも計算可) | 機体の偏角設定との差 |
| GNSS の状況 | 衛星数・DOP の予測 | 機体の `GPS_RAW_INT` / 衛星配置予測 | 飛行時間帯の予測 DOP が悪い |
| 日没・明るさ | 目視・カメラ | 計算 | 日没までの残り時間 |

- 飛行前: 飛行場所と時間帯の外的リスクを一覧にして示す(ブリーフィング)。
- 飛行中: 一定間隔(例: 10 分)で更新し、悪化したら知らせる。機体側の兆候(例: コンパス分散の上昇)と外的要因(例: Kp の上昇)が重なったら、兆候の重みを上げる。
- 外部サービスに届かないとき(現場にインターネットが無いなど)は「外的要因: 取得できず」と明示し、機体テレメトリだけで監視を続ける。最後に取得した値と取得時刻を表示する。
- 外部へ送るのは飛行場所の概略座標(例: 0.01° に丸め)だけ。

### 5.4 取得元は複数、総合判断(ユーザー決定 2026-10-24)

1 つの取得元に頼らず、使える取得元をできるだけ多く使い、複数源の情報を総合して判断する。

取得元の候補(利用規約・更新間隔・キーの要否は実装時に各サービスで確認する):

| 分類 | 取得元 | 得られるもの | キー |
|---|---|---|---|
| 気象(予報) | Open-Meteo(複数の数値予報モデル。JMA モデルを含む) | 地上・上空の風・突風、気温、降水、雲 | 不要 |
| 気象(観測) | 気象庁 アメダス(防災情報の JSON) | 最寄り観測所の風・気温・降水の実測 | 不要 |
| 気象(ナウキャスト) | 気象庁 雷ナウキャスト・降水ナウキャスト | 1 時間先までの雷活動度・降水 | 不要 |
| 気象(商用、任意) | OpenWeatherMap など | 予報・警報 | 要 |
| 機体自身 | `WIND`、`SCALED_PRESSURE`、バッテリー温度など | その場の実測 | — |
| 宇宙天気 | NOAA SWPC(`services.swpc.noaa.gov`) | Kp 指数(実測・予報・1 分推定)、警報、Dst | 不要 |
| 宇宙天気 | NICT 宇宙天気予報 | 日本向けの予報・警報 | 不要 |
| 宇宙天気 | GFZ Potsdam / 京都大学 WDC | Kp・Dst の確定値 | 不要 |
| 地磁気 | 世界磁気モデル(WMM、内蔵計算) | 偏角・伏角・全磁力 | — |
| GNSS | 衛星軌道(CelesTrak の軌道要素)から内蔵計算 | 飛行時間帯の衛星数・DOP 予測 | 不要 |
| 天文 | 内蔵計算 | 日の出・日没・薄明 | — |

総合判断の規則(決め打ち。LLM は結果の説明を担う):

- **安全側を採る**: 同じ要素(例: 突風)で取得元の値が割れたら、危険側(大きい方)を採用して判定する。
- **実測を優先**: 機体の実測 > 近傍の地上観測 > ナウキャスト > 予報の順に重みを付ける。古い値は鮮度に応じて重みを下げる。
- **不一致を知らせる**: 取得元どうしの差が大きいときは「取得元で値が割れています」と、それぞれの値と出典を示す。
- **出典と時刻を常に表示**: 判定の根拠ごとに取得元名と取得時刻を出す。
- **欠けても止まらない**: 取得元の一部が使えなくても、残りで判定を続け、欠けていることを示す。全部使えなければ「外的要因: 取得できず」(§5.3)。
- **機体側の兆候と組み合わせる**: 外的要因はそれ単独で介入はしない(警告と提案まで)。機体側の兆候と重なったとき、その兆候の判定を早める・重みを上げる。

#### 5.4.1 v1 の取得元(裁定 10、利用条件は 2026-10-25 に確認)

| 取得元 | v1 | 内容・条件 |
|---|---|---|
| Open-Meteo | 対応(既定オン、600 s) | `/v1/forecast` の current(気温・降水・風・突風・風向)と 80 / 120 m の風。無料 API は非商用(CC BY 4.0)なので設定ページに明記。キーを設定すると `customer-api` に切り替える |
| 気象庁 アメダス | 対応(既定オン、600 s) | `bosai/amedas` の `latest_time.txt` → `map/{時刻}.json`、観測所表(24 h キャッシュ)。座標は送らず、30 km 以内の最寄り観測所を手元で選ぶ。品質フラグ 0 だけ使う。出典「気象庁ホームページ」を値ごとに表示。契約 API ではないため形式が変われば取得元の失敗(`parse`)として扱う |
| 気象庁 雷・降水ナウキャスト | **未対応(v1)** | 地図タイル(PNG)だけでデータとして配信されていない。降水は Open-Meteo とアメダスで代替 |
| NOAA SWPC | 対応(既定オン) | Kp 観測(900 s)、1 分推定 Kp(300 s、ナウキャスト)、Kp 予報(3600 s、24 h 先までの最大)、警報(900 s、本文は信頼しない文字列として表示のみ)。Kp は見出し行つき配列とオブジェクト配列の両方を読む |
| GFZ Kp | 対応(任意、既定オフ) | 観測 Kp |
| 京都大学 WDC | **未対応** | HTML だけ |
| NICT 宇宙天気予報 | **未対応** | 2026-10-25 時点で機械可読の配信が見当たらない(HTML のみ)。設定ページに「機械可読の配信なし(未対応)」とリンクを出す |
| OpenWeatherMap | 対応(任意、キー必須、既定オフ) | 現在の天気(予報モデル扱い) |
| CelesTrak の軌道要素による DOP 予測 | **未対応(v1)** | SGP4 と複数衛星系の扱いが大きすぎる。GNSS は機体の `GPS_RAW_INT` の衛星数・HDOP(実測)で判定 |
| WMM・日の出 / 日没 | 内蔵計算 | `world_magnetic_model`(WMM2025)、NOAA の日の出・日没式 |

#### 5.4.2 鮮度・閾値・総合判断(裁定 11・12)

- 位置: 送るのは丸めた座標だけ(0.01° 既定、0.05° / 0.1° を選べる)。位置を使うのは Open-Meteo と OpenWeatherMap だけ(アメダスは手元で観測所を選ぶ)。最大 4 地点(fix ≥ 3 の接続機、無ければホーム)。取得のログには取得元・ホスト・丸めた地点だけを書き、生の位置や URL 全体(キーを含みうる)は書かない。位置が無ければ `no_location`。
- 鮮度: 実測 60 s、観測 30 分(Kp の観測は 4 h)、ナウキャスト 30 分、予報は取得から 3 h。古い値は時刻つきで灰色表示し、判定には数えない。
- 閾値(警告 / 強い警告。警告 = 機体の上限の 70 %): Copter 風 8.4 / 12 m/s・突風 10.5 / 15、QuadPlane 風 10.5 / 15・突風 12.6 / 18、固定翼 風 12.6 / 18・突風 15.4 / 22。全機種共通で降水 0.5 / 2.0 mm/h、気温 低 0 / −10 °C・高 35 / 40 °C、Kp 5 / 7、\|WMM − `COMPASS_DEC`\| 2 / 5°(`COMPASS_AUTODEC = 1` なら判定しない)、衛星数 < 10 / < 6・HDOP ≥ 2 / ≥ 4、日没まで 30 / 10 分(日没後・日の出前は強い警告)。
- 総合: 要素ごとにレベル = 新しい値のレベルの最大(気温は最小値を低温側、最大値を高温側で判定)。表示の値はそのレベルを決めた値、先頭に出すのは最上位の分類(実測 > 観測 > ナウキャスト > 予報)の最も新しい値。値の差が風・突風 3.0 m/s、気温 5 °C、降水 1.0 mm/h、Kp 2.0 以上なら「取得元で値が割れています」。取得に失敗した有効な取得元は「欠け」に並べ、有効な外部取得元のどれにも新しい値が無ければ「外的要因: 取得できず」(最後の値と時刻は表示し続ける)。v1 で検知の感度に使うのは Kp だけ(§5.1.1)。
- 通信: `reqwest`、リダイレクトは追わない、取得元ごとのタイムアウト、本文 2 MiB まで。エラー区分 `timeout` / `unreachable` / `http_<status>` / `redirect` / `parse` / `too_large` / `no_key` / `no_location`。取得は検知とは別のタスクで動き、検知は最新の結果を読むだけ(取得が止まっても監視は止まらない)。
### 5.5 アプリ設定「外的要因データ」ページ

アプリ設定に専用ページを設け、取得元を管理する(admin のみ編集可、変更は監査ログ)。

- 取得元ごと: 有効 / 無効、API キー(必要なものだけ。保存は暗号化 or 設定ファイル側、画面には末尾のみ表示)、更新間隔、タイムアウト
- 状態表示: 最終取得時刻、成功 / 失敗とエラー内容、次回取得予定、「今すぐ取得」
- 判定閾値: 風・突風・降水・気温・Kp などの警告 / 強い警告の閾値(機体の種類ごとに既定値)
- 位置の丸め精度(既定 0.01°)と、外部送信の同意状態(§3 の 2)
- オフライン時の挙動の説明
- v0.4 の決定(裁定 13・14):
  - API キーは設定ファイル / 環境変数だけ(`[env] openweathermap_api_key_env = "OWM_API_KEY"`、`open_meteo_api_key_env = "OPEN_METEO_API_KEY"`)。画面は「キー: 設定ファイルで設定済み …ab12」(末尾 4 文字)か「未設定(config.toml の [env])」だけを示す。画面でのキー編集・DB への暗号化保存は v1 の対象外。
  - 取得元ごとの既定: 更新間隔 60〜86 400 s、タイムアウト 1 000〜30 000 ms(既定 8 000 ms)。
  - 設定画面は新しいメンテナンスタブではなく、アプリ設定の 2 枚のカード「実験機能」「外的要因データ」から開くシートにする。admin 以外は読み取りのみ。
## 6. 判断の優先順位(全事象共通の枠)

候補動作ごとに予測経路と区域を照合し、上位ほど重いコストで比較する。

1. 人(作業員・通行人の区域)
2. 第三者の財産(隣の建物など)
3. 点検対象の建物(接触)
4. 他の機体
5. 自機
6. ミッション・点検データ

区域(人のいる区域 / 飛行禁止 / 建物の輪郭+安全距離 / 安全な着陸地点)は飛行前に地図で描く。トイレットボウルの対処(モード切替のみ)は経路を選ばないため、この版では記録と表示だけに使う。

## 7. 構成と機上 AI との連携

### 7.1 移植できる判定部

- 検知と方針は新しい純粋なクレート(例 `rgcs-guard`)に置く。入力 = 機体の時系列テレメトリ(位置・速度・姿勢・方位・EKF 状態・モード・目標)、出力 = 判定(事象・確度・根拠)と推奨動作。I/O・サーバー・非同期に依存しない。
- 同じクレートを、GCS(rgcs-server)と、将来の機上ノード / 機上 AI の両方で動かせるようにする(依存を最小にし、no_std 化の余地を残す)。
- 方針の設定(有効な事象・レベル・閾値・区域)は 1 つのデータ形式にし、GCS から機上へ配る(当面は RGCS の DB、将来は MAVLink FTP などで機上へ)。
- v1 の実装: `crates/rgcs-guard`(依存は `serde` だけ。I/O・非同期・サーバー型なし。`Sample`、局所 ENU と Kåsa 円当てはめ、`ToiletBowlDetector::push(&self, …) -> (Self, Verdict)`、`ExternalContext` による感度、`RcWatch`、純粋な状態機械 `Intervention::step(&self, policy, input) -> (Self, Vec<Effect>)`、`DecisionRecord` と `replay`)。外的要因の規則と解析器は `crates/rgcs-env`(取得はサーバー側)。テレメトリは `rgcs-mavlink` の guard タップ(`EKF_STATUS_REPORT` / `RC_CHANNELS` / `WIND` / `GLOBAL_POSITION_INT` / `MISSION_CURRENT` / `EXTENDED_SYS_STATE`)から、取りこぼしてもリンクを止めない `broadcast` で受ける(裁定 9)。
### 7.2 GCS と機上 AI の役割分担

- 機上 AI があれば、機上を優先する(遅延が小さく、リンク断でも動く)。GCS 側は監視・表示・人への通知と、機上 AI が無い機体の代行。
- (v1 の対象外。記録には担当を表す `owner: "gcs"` だけを入れておく。裁定 16)
- 二重操作を防ぐため、介入は「担当」を 1 つに決める: 機上 AI が介入したら機体からその旨を通知し(例: 専用コンポーネント ID の HEARTBEAT + STATUSTEXT、将来は専用メッセージ)、GCS はその機体への自動操作を止めて表示だけにする。
- 機上のローカル LLM も、判定は §5 の決め打ちルールが行い、LLM は状況説明・人への報告文・提案を担う(GCS の AI チャットと同じ役割分担)。

## 8. 記録と検証

- 判定ごとに: 入力の要約、各兆候の値、判定、選んだ動作、取り消し・引き継ぎの有無と時刻を記録し、飛行記録から再生できるようにする。
- SITL シナリオ: コンパスのオフセットや干渉を模擬するパラメータ(試験用 SITL のみで設定)でトイレットボウルを起こし、検知時間・誤検知・切替を確認する。風だけのドリフトで発動しないことも確認する。
- 実機の過去ログ(トイレットボウルが起きた飛行)があれば、それで閾値を決める。
- v1 の記録(裁定 8): 状態が変わるたびに `guard_decisions` へ 1 行(`record` = `{version: 1, config, context, samples(窓、最大 120), last_detected_ms, verdict, phase, action, by, owner, ts}`、飛行 ID つき、最新 5 000 行)。`rgcs_guard::replay(record)` は記録時と同じ判定を返す。設定変更と操作は監査ログ(`target = 'ai_intervention'`)。再生画面は v1 の対象外(`GET /api/guard/decisions` で取り出せる)。

### 8.1 試験用 SITL での確認(v1、2026-10-26)

- ハーネス: `tests/sitl/guard_toilet_bowl.py`(python3 標準ライブラリのみ)。試験用サーバー(8110)と試験用 SITL(Copter `-I6` = tcp:5820 / RC udp:5561、QuadPlane `-I7` = tcp:5830 / RC udp:5571)だけを相手にし、開発環境のポート(8000、5760–5793、RC 5501–5531 など)を指定すると起動を拒む。RC は UDP で 50 Hz(ch1–4 中立)、スティック操作は ch1 を 1600 µs に 1 s。
- 故障の設定は試験用 SITL の第 2 MAVLink ポート(SERIAL1)へ直接 `PARAM_SET` / 再起動する。サーバーはアーム中のパラメータ書き込みを拒む(spec 70 のインターロック)ため、飛行中の変更はサーバーを通せない。
- 2 種類のうず:
  - `--bowl compass`(現実の故障): コンパスの取付向きの誤り(`COMPASS_ORIENT`、既定 2 = 90° + ハードアイアン 40° 相当)を地上で設定して SITL を再起動し、EKF がその向きに合わせた状態で離陸する(ArduPilot の autotest と同じ作り方)。コンパス 1 台、GSF ヨーリセット無効、EKF フェールセーフ無効、コンパスの事前チェックだけ省略(FC の LAND がガードより先に動かないように)。
  - `--bowl wind`(処理系の確認): 位置保持を弱め(`LOIT_ANG_MAX 5`)、風向を 30°/s で回しながら風速を上げる。機首は動かず、半径が増える円を描く(兆候 A + B)。毎回同じように起きるので、検知 → カウントダウン → モード切替 → 引き継ぎの流れの確認に使う。
- 記録したテレメトリは `crates/rgcs-guard/tests/fixtures/sitl_copter_*.jsonl`、判定記録は `sitl_decisions.json` に置き、`tests/sitl_replay.rs` で再生する。

### 8.2 結果(Copter、2026-10-26)

| シナリオ | 結果 |
|---|---|
| A 定常風 8 m/s・LOITER 60 s | 警告 0 件(2 回) |
| B 風のうず・L2・RC 引き継ぎ | LOITER から 29.8 s(回転が 10 s で 270° に達した時点)で検知 → カウントダウン → 5.15 s 後に ALT_HOLD → ch1 を動かして 0.51 s で「引き継ぎ済み」 |
| C 同上・L2・画面の「取り消し」(Kp 7.33) | バナーに「宇宙天気(Kp)により感度を上げています」、取り消し後 15 s LOITER のまま。監査 `cancel` |
| D 同上・L3・RC 操作なし(外的要因の偽サーバー停止中) | 検知と同時に ALT_HOLD、20.1 s 後に「引き継ぎが確認できません」、ガードの `set_mode` はこの飛行で 1 件だけ。外部取得が全部失敗しても監視は続く |
| コンパス故障(6 回) | LOITER に入ってから 10 s(窓が埋まる最短)〜65 s で検知。SITL の EKF3 では、90° 前後の誤りは半径 1.5 m 前後で収まっていく渦、135° では 10 s ごとの位置リセットを伴う暴走になり、検知が続かない。L2 ではカウントダウン後の再確認(直近 1 s に検知)が 6 回とも成り立たず、モードは切り替えなかった(渦が自然に収まった場合は正しい動き) |
| QuadPlane(`-I7`) | 風のうずは翼と風見で円にならず、コンパス故障は離陸中に EKF が向きを直し、検知まで至らなかった。QHOVER の選択は単体・サーバーテストで確認 |

既定値は変えていない: コンパス故障の SITL データ(`sitl_copter_toilet_bowl.jsonl`)は半径 1.55 m で頭打ちになり縮む渦で、検知器は半径が 1.5 m を超えて増えている間だけ「検知」とする。明らかな見逃しではない。実機の過去ログで見直す(§10)。
