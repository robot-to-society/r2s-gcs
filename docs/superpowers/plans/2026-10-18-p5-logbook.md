# P5 Inspections + MLIT Logbook Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Pre-flight checklists (様式 2), automatic flight-record drafts from ARM → DISARM (様式 1), maintenance records (様式 3), DataFlash log retrieval, and per-vehicle PDF / CSV export of the three MLIT forms, filling the 日常点検 / 飛行日誌 / アプリ設定 tabs of the maintenance view.

**Architecture:** One migration (`0004_logbook.sql`) adds the registry columns and six record tables; rgcs-core gains the wire types (ts-rs) and a JST date helper; rgcs-store gains one module per record family. The server adds a 1 Hz `FlightTracker` over the router states, a `LogHub` speaking LOG_REQUEST_LIST / LOG_REQUEST_DATA, a `pdf/` module (printpdf 0.12 without default features, Noto Sans JP OTF embedded with `include_bytes!`, our own wrap + table engine) and a CSV writer, exposed through `logbook_api` / `flight_api` / `logs_api` / `export_api`. The UI adds `features/logbook/` (日常点検 tab, 飛行日誌 tab with four sub-tabs) and `features/app-settings/` (表示言語 / 機体台帳 / 操縦者 / 点検テンプレート), enabling the three disabled tabs of `MaintView`.

**Tech Stack:** Rust (axum 0.8, sqlx SQLite, tokio, printpdf 0.12 `default-features = false`, csv 1.4, time 0.3, tokio-util `io`), mavlink 0.19 (common dialect LOG_* messages), React 19 + TypeScript + Vite + vitest + Playwright, ts-rs 12 bindings.

**Spec:** `docs/superpowers/specs/2026-10-17-year-end-demo-design.md` §5.5, §5.6, §5.7 (メンテナンス / 飛行日誌タブ / アプリ設定), §5.8, §5.9, §7-4, §7-5, §9 (校正は表示のみ、ログは 2 経路); roadmap row P5 in `docs/plan/implementation-plan.md`; MLIT 「無人航空機の飛行日誌の取扱要領」 (forms 1–3; column titles quoted in Task 8). Prior art to follow: `docs/superpowers/plans/2026-10-18-p4-params.md` (ParamCache / param_api shapes), `apps/rgcs-server/src/missions.rs` (hub with frame broadcast).

## Global Constraints

- Immutable data in the UI (new objects, never mutate); files ≤ 400 lines (800 max), functions < 50 lines; TDD (red first); no `console.log`; no secrets in code; input validated (zod on the UI side, `TryFrom`/explicit checks on the server).
- Never `window.confirm`; the existing confirm-token flow is for vehicle commands only — logbook writes are plain authenticated POST/PUT/PATCH (CSRF header via `apiFetch`).
- `0001_init.sql` is never edited; new columns/tables go in `crates/rgcs-store/migrations/0004_logbook.sql` (spec 60 §5: additive only).
- Record tables are append-only: corrections are a new row with `supersedes = <old id>`; lists and exports hide superseded rows (addendum §5.8).
- Flight = first ARM … last DISARM; a re-ARM within 10 min continues the same flight; takeoff/landing times are JST minutes; flight time is minutes rounded **up**; total = registry initial minutes + landed flights (addendum §5.6).
- 「飛行日誌は機体毎」: every list, form and export is scoped to one `sysid` (addendum §5.6).
- Log retrieval has two routes (addendum §9): browser upload of a `.bin` (always available) and MAVLink fetch (enabled by `config.toml` `log_fetch = "auto" | "on" | "off"`, where `auto` = on for tcp/udp links and for serial links at ≥ 921600 baud).
- PDF generation is server-side with Noto Sans JP embedded (addendum §5.6); the font file lives in `assets/fonts/` with its OFL licence and is fetched by `scripts/sync-fonts.sh`.
- 点検・校正 stays disabled in P5 (roadmap P5 row does not list it; addendum §9 defers calibration to a parameter-derived display after the demo).
- Commit messages: conventional commits, no `.claude/` ever staged; `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>` trailer.
- Design: copy the Glass prototype's classes (`.surface`, `.form`, `.kv`, `.tbl`, `.seg`, `.in`, `.btn`, `.badge`, `.warnbox`) and the `glass_maint_app.png` card layout; finish with the screenshot comparison in `.dev/design-sync/compare.html` before asking the user to review.

## Review Focus

1. **Re-ARM within 10 min** after a DISARM must extend the same flight (one draft, landing time moved), while a re-ARM after 10 min starts a new draft — Task 6 `rearm_within_window_extends_the_flight` / `rearm_after_window_starts_a_new_flight`.
2. **Link lost while armed** (crash, battery pull): the open flight must be landed at the last heartbeat time once the link has been lost for 10 min, never left open forever — Task 6 `lost_link_lands_the_flight_at_last_rx`.
3. **Export with no data** (vehicle never edited in the registry, zero flights/runs/records in the range): a valid PDF/CSV with the header block and an empty table, no 500 — Task 8 `empty_range_renders_a_one_page_form`.
4. **A dropped LOG_DATA chunk** during a fetch must be re-requested from the first missing offset and the saved file must be byte-identical to the FC log — Task 7 `dropped_chunk_is_re_requested_and_the_file_is_exact`.
5. **Editing a confirmed flight** must not rewrite history: the PATCH creates a superseding row and lists/exports show only the newest — Task 3 `patch_on_a_confirmed_flight_supersedes_it`, Task 5 `confirmed_flight_patch_returns_the_superseding_row`.

Also pinned (secondary): inspection POST whose `results` count ≠ template item count → `400 validation` (Task 4); deleting a template assigned to a vehicle clears the assignment and the vehicle falls back to the default template (Task 2); a vehicle with no GPS fix (lat = lon = 0) records `None` positions, not 0,0 (Task 6).
