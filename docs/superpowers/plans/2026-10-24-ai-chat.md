# AI Chat (AI 操作メニュー) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Enable the AI チャット right panel on the operations map (spec 10 §3.4, `glass_ops_ai.png`). The operator asks questions in Japanese or English. A server-side agent answers with read-only tools and may **propose** vehicle commands. Scope is 「提案のみ」 (user decision 2026-10-24):
- **Read tools:**
  - `get_vehicle_status`;
  - `list_recent_messages`;
  - `search_log`;
  - `list_vehicles`.
- **`propose_command`:** returns a validated proposal card. It never sends anything.
  - The UI shows the card (command, target, parameters, the AI's reason, 実行 / 却下).
  - Only the operator's 実行 press sends the command, through the existing path: `ConfirmDialog` for `requires_confirm` commands, server prechecks, the vehicle audit row linked to the proposal id.
  - The AI never sends anything to a vehicle or a camera.
- **Two LLM providers, chosen in `config.toml [ai]`:**
  - Claude through the Anthropic Messages API with tool use (default model `claude-sonnet-5-5`);
  - a local OpenAI-compatible endpoint (`/v1/chat/completions` with `tools`, e.g. Ollama).
  - The API key comes from the server config or an env var only. It is never returned to the UI and never logged.
  - The panel shows the active provider / model, and a clear 「AI 未設定」 state when nothing is configured.
- **Nav:** the AI チャット nav button is enabled. Like the prototype's `toggleAi`, it opens the panel on the ops map; it is not a separate view.

**Architecture:**
- **New crate `crates/rgcs-ai`** (spec 30 §2: 「LLM アダプタ、ツール定義」; rule analysis stays out, see Out of scope). It knows nothing about axum or `AppState`:
  - `config.rs`: `AiConfig`, `ProviderKind`, `Secret` (redacting `Debug`, no `Serialize`).
  - `llm.rs`: the provider-neutral `Turn` / `Block` / `LlmRequest` / `LlmResponse` and `trait LlmClient`.
  - `anthropic.rs` / `openai.rs`: one adapter per wire protocol. Both use `reqwest` with JSON, non-streaming.
  - `tools.rs`: JSON schemas for the 5 tools and `parse_call(name, input) -> Result<ToolCall, ToolError>`.
  - `prompt.rs`: the fixed Japanese system prompt.
  - `agent.rs`: `run_turn(...)`, the bounded tool loop. It works against `trait ToolHost`, which the server implements.
  - `testing.rs` (behind feature `fake`): `ScriptedLlm` (in-process) and `FakeProviderServer` (axum, both protocols, scripted replies, records requests).
- **Server (`apps/rgcs-server`):**
  - `ai_hub.rs`: `AiHub` (cloneable, `Arc<std::sync::Mutex<…>>` inside) holds the conversations (per user, bounded, TTL), the per-user rate limit and in-flight flag, the proposal store and the rolling token budget.
  - `ai_tools.rs`: `ServerTools` implements `ToolHost` from `AppState`: router, `store.messages`, the new `store.search_messages`, video status. Every call is audited with target `ai`.
  - `ai_validate.rs`: `validate_proposal` reuses `commands::precheck`, `commands::vtol_unknown` and `VehicleCommand::invalid`, plus proposal-only rules (mode names per airframe, speed range, `other` / `change_alt` rejected).
  - `ai_api.rs`: `GET /api/ai/status`, `POST /api/ai/chat`, `POST /api/ai/proposals/{id}/dismiss`.
  - `commands.rs`: `CommandBody` gains `ai_proposal_id: Option<String>`. When present, the proposal must exist, be pending, belong to the caller, match `(sysid, command)` and be unexpired. It is marked executed and its id is written into the vehicle audit row's `args`.
- **Core types (`rgcs-core/src/ai.rs`, ts-rs):** `AiStatus`, `AiProviderKind`, `AiChatRequest`, `AiChatReply`, `AiToolRun`, `AiStatusCard`, `AiVideoState`, `AiProposal`.
- **Mode list:** `rgcs_mavlink::modes::modes_for(kind, vtol) -> &'static [&'static str]` is the Rust mirror of the UI `modesFor(...).all`.
- **UI:**
  - `features/ai/` holds pure modules (`chat.ts` reducer, `api.ts`, `format.ts`) and thin components (`AiPanel`, `ChatItemView`, `ToolCard`, `ProposalCard`).
  - `app/rightPanel.ts` holds the pure nav ↔ right-panel state.
  - `Shell` renders `AiPanel` in place of `DetailPanel` when `right === 'ai'`.
  - Execution goes through `useCommandRunner.pick(sysid, command, {aiProposalId})`.
  - Prototype class names are reused (`.g.panel.float.float-r`, `.panel-h`, `.bubble.user`, `.bubble.bot`, `.inset`, `.row`, `.hair-t`, `.in.lg`, `.btn.btn-lg.btn-primary`). Layout bits the prototype inlines go in a new `styles/ai.css`.

**Tech stack:** Rust (tokio, axum 0.8, reqwest 0.12 with `json` + `rustls-tls`, serde_json, ts-rs), React 19 + TypeScript (vitest, @testing-library), lucide-react, Playwright (headless check only), python3 stdlib (scratch fake LLM for the live check only).

## Rulings (spec gaps / open questions decided here)
1. **The panel is opened from the nav, not a view.**
   - `Shell` keeps `right: 'detail' | 'ai'` beside `view`.
   - Nav `ai` → `navigate({view, right}, 'ai')`: if `view === 'ops' && right === 'ai'`, it returns `{view: 'ops', right: 'detail'}`; otherwise it returns `{view: 'ops', right: 'ai'}`, which closes modals and the cockpit like the prototype.
   - Nav `ops` → `{view: 'ops', right: 'detail'}`. Any other nav target keeps `right` unchanged.
   - The lens follows `navViewOf(view, right)`: `'ai'` when `view === 'ops' && right === 'ai'`, otherwise `view`.
   - `ENABLED_VIEWS` gains `'ai'`, but `view` is never set to `'ai'`.
   - The panel's X sets `right = 'detail'`.
   - The AI panel replaces `DetailPanel` while open, even with no vehicle selected, so the stage's `noright` class is off while it shows.
   - The 全コマンド dock stays available (`beside` = true).
   - The nav's accent dot is not drawn: there is no unread state.
2. **Proposals.**
   - `propose_command(sysid, command, reason)` validates as in the fixed-values table and stores an `AiProposal` (pending). The tool result to the LLM is `{proposal_id, status: "shown_to_operator"}` or `{error: code, message}`.
   - The reply carries the proposals. The UI renders each one as an AI-labelled card.
   - 実行 calls `runner.pick(sysid, command, {aiProposalId})`. For `requires_confirm` commands the normal `ConfirmDialog` opens with an extra line 「AI の提案」 and the reason.
   - The server checks `ai_proposal_id` before the confirm-token check. It returns:
     - `404 proposal_not_found`;
     - `403 forbidden` (another user's proposal);
     - `409 proposal_mismatch` (sysid or command differs);
     - `409 proposal_expired`;
     - `409 proposal_used` (already executed or dismissed).
     - All five are audited `rejected`.
   - On acceptance into the queue it marks the proposal `executed` (one use only).
   - 却下 → `POST /api/ai/proposals/{id}/dismiss` (audited `dismiss_proposal`).
   - A proposal is validated twice, at proposal time and at execution. The live state may change in between; the execution-time precheck decides.
3. **Wire protocols are hand-written over `reqwest`.** Rust has no official Anthropic SDK; raw HTTP is the supported path.
   - **Anthropic.** Assistant `content` blocks are stored **verbatim** (`Block::Opaque(serde_json::Value)` for `thinking` and any unknown block type) and replayed unchanged on the next call. Sonnet 5.5 binds thinking blocks to the conversation, and editing them can 400.
   - Stop reasons:
     - `tool_use` → run the tools; every `tool_result` goes back in **one** user message, `is_error: true` on failures;
     - `end_turn` → done;
     - `max_tokens` → done with `truncated: true`;
     - `refusal` → `AiError::Refused` → `502 ai_refused` 「AI が応答を拒否しました」;
     - anything else → `502 ai_provider_error`.
   - Tool inputs are parsed as JSON values, never string-matched.
   - **OpenAI-compatible.** `tool_calls[].function.arguments` is a JSON **string**; when it fails to parse, the tool returns `{error: "invalid_json"}`. `finish_reason` maps `tool_calls` → tools, `stop` → done, `length` → truncated. Assistant messages are rebuilt from `Block`s (`content` + `tool_calls`), and results go back as `role: "tool"` messages with `tool_call_id`.
   - Server-side fallbacks (`fallbacks`, beta `server-side-fallback-2026-07-01`) are **not** sent. A refusal is rare for this domain, and the error state is clear. This is listed in Out of scope.
4. **Non-streaming.** `POST /api/ai/chat` returns one `AiChatReply` when the loop ends. While it waits, the UI shows a bot bubble with a spinner (`IconLoader`, `.spin`) and 「考えています…」. Streaming (SSE / WS) is out of scope.
5. **History is per conversation, append-only, bounded by refusal, not by trimming.** Dropping old turns would edit history and invalidate Anthropic thinking blocks. When a limit is hit, the server answers `409 conversation_full`, and the panel shows 「会話が長くなりました」 with a 新しい会話 button that clears `conversationId`.
   - Changing the 対象 select does **not** reset the conversation. Each user message is sent with the current `sysid`, and the server prefixes the user text with `[対象機体: UAV-03 (sysid 3)]`.
   - Conversations live in memory only. A server restart loses them, and the UI treats `404 conversation_not_found` as a new conversation (it retries once without the id).
   - The UI keeps its items in component state; switching views keeps them because the panel state is lifted to `Shell` (`useAiChat`).
6. **Timeouts and cancellation.** The chat handler wraps `run_turn` in `tokio::time::timeout(chat_timeout)`. On timeout the in-flight flag is cleared by a guard's `Drop`, and the conversation is **not** appended: the user turn is dropped with it, so a later retry is clean.
7. **Cost guard.**
   - Per-request token cap, a server-wide rolling 24 h budget (`AiHub` keeps `(ts, tokens)` entries and prunes those older than 24 h), a per-user rate limit and one chat in flight per user.
   - There is no per-dollar accounting: models and prices change.
   - `/api/ai/status` reports `budget_left` (or `null` when unlimited).
8. **Prompt-injection posture.**
   - Vehicle text (STATUSTEXT, vehicle names, mode strings, audit text) reaches the model only inside tool results, as JSON values under keys named `untrusted_text`.
   - The system prompt says that tool output is data from vehicles and logs, that instructions in it are never followed, and that proposals must come from the operator's request.
   - Because the AI cannot send anything, the worst case is a misleading proposal. The guards are:
     - the card is visibly labelled 「AI の提案」 with the bot icon;
     - the operator presses 実行;
     - `requires_confirm` commands go through the hold-to-confirm dialog;
     - server prechecks and the proposal TTL apply;
     - each proposal is single-use.
9. **`search_log` searches the stored message log, not DataFlash.** It searches the SQLite `messages` table (STATUSTEXT, system messages, command results; `KEEP_ROWS = 5000`) through a new `Store::search_messages(query, sysid, since, limit)` with `LIKE ? ESCAPE '\'`, escaping `%`, `_` and `\`. There is no `.bin` / tlog parser yet (`rgcs-log` does not exist), so DataFlash search is out of scope. The tool description says so, so the model does not promise it.
10. **The tool card** (screenshot) is built from the **last** `get_vehicle_status` call in the reply:
    - 最終受信 = `now − last_rx_ms`, shown as 「1.8 秒前」;
    - 映像 = `AiVideoState` text (受信中 / 未接続 / 確認中 / なし), because the server has no frame age (the design's 「0.2 秒前」 cannot be produced honestly).
    - ツール実行履歴 lists every `AiToolRun` of the reply: `IconOk` green when ok, `IconError` red when error / rejected; the tool's ja label + 「・完了」 / 「・失敗」; the time; 「対象: UAV-03」 when it has a sysid.
    - A reply without a status call shows only the history block.
11. **Unconfigured.** `[ai]` absent or `provider = "none"` → `AiStatus {configured: false, reason: "disabled"}`. Anthropic without a key → `reason: "no_api_key"`. The panel shows an inset 「AI は未設定です（config.toml の [ai]）」, disables the input, and the nav button stays enabled. `/api/ai/chat` → `503 ai_unconfigured`.
12. **Access.** Any logged-in user (`AuthUser`, operator or admin) may chat. Executing a proposal goes through the command endpoint with the same rights as a direct command. Conversations and proposals are visible only to their owner.

## Review Focus (untested-in-isolation failure modes most likely to bite an operator)
1. **A proposal turns into a send without a human press.** Check that:
   - no code path from `run_turn` / `ServerTools` reaches `app.queue`, `app.outgoing`, `app.cameras`, `app.mav` or `roi`. `ai_tools.rs` must not import `commands::command` or any camera API; grep it in review;
   - the UI never calls `runner.pick` from an effect, only from the 実行 `onClick`;
   - a proposal is single-use, and expiry is checked server-side.
2. **The key leaks.** Through:
   - `Debug` of the config;
   - a reqwest error that echoes headers;
   - a provider error body;
   - a `tracing::error!(?req)`;
   - the `/api/ai/status` body.
   - The redaction test covers `Debug`, the responses and the error strings. A reviewer greps for `api_key` in every `tracing::` call.
3. **A runaway loop or bill.** A model that keeps calling tools, or a fake that always answers `tool_use`, must stop at 6 iterations plus 1 forced-text call. The per-chat token cap must count every call, including the forced one. The rolling budget must persist across conversations. Test with `ScriptedLlm::always_tool_use()`.
4. **History corruption.** On Anthropic, the replayed assistant blocks must be byte-equivalent JSON values (thinking blocks included). A timed-out or failed turn must not leave a dangling `tool_use` without its `tool_result`, which 400s every later call. Commit the turn to the conversation only after `run_turn` returns `Ok`.
5. **Stale or misleading proposals.**
   - The state can change between proposal and press (the AI proposes `arm` and someone else arms first). The execution precheck must still refuse with the normal reason, shown on the card.
   - A proposal for a vehicle that went `link: lost` must fail with `link_lost`.
   - A mode valid on the wrong airframe (`QLOITER` on a copter) must be refused at proposal time.
   - The live check exercises one confirm-dialog command (`arm`) and one direct command (`set_mode`).
