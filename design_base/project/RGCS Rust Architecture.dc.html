RGCS — ArduPilot 複数機体対応 GCS
Rust アーキテクチャ設計書

v0.1 ドラフト · 2026-10-14 · 対象 OS: macOS / Windows / Ubuntu · GUI: Tauri 2 (Rust バックエンド + Web UI)

1. 目的と設計方針

RGCS は ArduPilot(Copter / Rover)を同時に多数(20 機超)監視・制御する地上局アプリである。オフライン運用、日英切替、2 系統ジョイスティック(機体・ジンバル)を必須要件とし、プロトタイプ(RGCS Prototype)の 10 画面を実装対象とする。

  • 安全最優先 — 機体への送信は必ず Rust 側のコマンドキューを経由し、確認・レート制限・操作履歴記録を一元化する。UI から MAVLink を直接触らない。
  • コアを UI から分離 — rgcs-core 群は Tauri に依存しない純 Rust クレートとして設計し、CLI・SITL テスト・将来の別 UI から再利用できる。
  • オフライン前提 — 地図タイル(MBTiles)、地形、パラメータ定義、AI モデルの全てをローカルに持ち、ネットワークは「あれば使う」扱い。
  • 多機体スケール — 機体ごとの状態はロックフリーな watch チャネルで配信し、UI は 10 Hz に間引いた差分のみ受け取る。

4.1 多機体ルーティング

  • リンク(シリアル / UDP / TCP)と機体は多対多。Router が受信フレームの (system_id, component_id) で VehicleHandle に振り分け、未知の sysid は自動登録して VehicleDiscovered イベントを発火。
  • 送信は Command { target, msg, policy } を CommandQueue に投入。policy で「ACK 必須・再送 3 回・1.5 s タイムアウト」等を宣言し、結果は CommandResult として UI とメッセージ欄へ返す。
  • HEARTBEAT 欠落 3 s で CommsDelay(黄)、10 s で LinkLost(赤)を機体メッセージに積む。プロトタイプの「通信遅延」はこのイベント。

4.2 テレメトリ配信

受信は最大レート(50 Hz 超)で VehicleState を更新し、UI 向けには 10 Hz のタイマで直前値との差分(位置・姿勢・バッテリ・モード)のみ telemetry:{sysid} イベントで emit する。20 機 × 10 Hz でも IPC 量は数十 KB/s に収まる。

4.3 コマンド安全策

  • ARM / DISARM / RTL / LAND / モード変更は UI で確認ダイアログ、Rust 側でも requires_confirm を検査し、確認トークン無しの呼び出しは拒否。
  • 全送信を audit_log(operator, vehicle, command, result, ts) に記録。オペレータ未登録時は送信系コマンドを無効化(プロトタイプの「未登録」状態)。
  • Guided 移動は SET_POSITION_TARGET_GLOBAL_INT。高度は「現在維持 / 指定(ホーム相対)」の 2 択で、ジオフェンス上限を超える値は送信前に弾く。

5. サブシステム設計

5.1 映像(rgcs-video)

  • 機体ごとに GStreamer パイプライン(rtspsrc → decodebin → tee → [appsink | filesink(mp4)])。ARM 検知で AUTO REC 開始、DISARM で停止。
  • WebView への表示: 第 1 候補はローカル WebRTC(webrtcsink)、代替として appsink → 共有メモリ → canvas 描画。6 面同時でも GPU デコードで CPU 負荷を抑える。
  • 未接続は VideoState::Disconnected を UI に通知(「映像未接続」タイル)。

5.2 地図(rgcs-map)

  • axum で http://127.0.0.1:{port}/tiles/{z}/{x}/{y} を提供。MBTiles を優先し、無ければオンラインソースから取得してキャッシュに書き戻す(「地図キャッシュを更新」)。
  • 3D 表示は MapLibre の terrain(ローカル Terrain-RGB タイル)+ pitch。機体マーカは高度に応じて地表からの引出線を描画。
  • 運用エリアの事前ダウンロード(ズーム範囲・矩形指定)は rgcs-cli tiles fetch と UI の両方から実行可能。

5.3 ログ・AI 解析(rgcs-log / rgcs-ai)

  • DataFlash .bin を FMT/FMTU に基づきストリーミング解析し、polars DataFrame 化。VIBE, RCOU, ATT, GPS, BAT, MODE, ERR を標準抽出。
  • ルール解析(例: VIBE ピークと RCOU 分散の同時発生 → 「モーターバランス/プロペラ」候補)を先に実行し、LLM には抽出済みの根拠データだけを渡して説明文を生成。根拠は「VIBE」「モーター出力」のようにチップ化して UI に返す。
  • 「該当区間にジャンプ」は LogCursor { t_start, t_end } イベントで全チャート・経路地図を同期。
  • 運用中の AI チャットはツール呼び出し(get_vehicle_status, list_recent_messages, search_log)のみ許可。機体への送信ツールは提供しない。

5.4 ジョイスティック(rgcs-input)

  • gilrs で複数デバイスを列挙し、「機体操作」「ジンバル操作」に別デバイス(同一デバイス可)を割当。設定は input_profiles テーブルに保存。
  • 機体操作: 軸 → MANUAL_CONTROL(50 Hz)または RC_CHANNELS_OVERRIDE(設定で選択)。対象は「選択中の機体」のみ、切替時は 0.5 s ニュートラル送信。
  • ジンバル操作: GIMBAL_MANAGER_SET_PITCHYAW / DO_MOUNT_CONTROL。デッドゾーン・感度・反転はプロファイル単位。
  • デバイス切断を検知したら即座に機体へニュートラルを送り、メッセージ欄に警告。

5.5 ミッション作成(rgcs-mission)

  • ミッションは Mission { name, vehicle, items: Vec<MissionItem> } として保持。MissionItem は MAV_CMD(TAKEOFF / WAYPOINT / LOITER_TIME / DO_SET_ROI / LAND / RTL)+ 座標・高度(ホーム相対)・待機秒・半径。UI の編集は全てこの構造体への純粋な差分操作(追加・並べ替え・ドラッグ移動)で、Undo/Redo はスナップショットで実装。
  • 機体への書込は MAVLink Mission Protocol(MISSION_COUNT → MISSION_REQUEST_INT → MISSION_ITEM_INT → MISSION_ACK)を状態機械で実装し、タイムアウト再送と途中失敗時のロールバックを行う。読込は逆方向。
  • 保存形式は QGC/Mission Planner 互換の .waypoints(テキスト)と、RGCS 独自メタ(名前・対象機体・既定高度)を含む .rgcsmission(JSON)の 2 種。
  • 検証: 高度上限(FENCE_ALT_MAX)・ジオフェンス外・総距離に対するバッテリ余裕・最初の項目が TAKEOFF でない等を書込前に警告し、致命的なものは送信を拒否。

5.6 パラメータ / メンテナンス(rgcs-mavlink)

  • 接続時に PARAM_REQUEST_LIST で全取得し機体別キャッシュ。UI の「推進・モーター」等の分類は同梱の apm.pdef.xml から生成。
  • 変更はドラフト → 「機体に書き込む」で PARAM_SET + 読み戻し検証。差分と担当オペレータを param_history に保存(「変更履歴」タブ)。
  • 校正(加速度計・コンパス・RC・ESC)は MAV_CMD_PREFLIGHT_CALIBRATION と進捗 STATUSTEXT を状態機械で追跡。

7. スレッド / タスクモデル

  • tokio マルチスレッドランタイム 1 つ。リンク受信・コマンドキュー・テレメトリ間引き・映像状態監視は各タスク。
  • GStreamer と gilrs はブロッキング API のため spawn_blocking または専用 OS スレッドで駆動し、チャネルで tokio 側へ渡す。
  • ログ解析(数百 MB)は rayon 並列で別スレッドプール。進捗を analyze_progress イベントで通知。

9. テスト戦略

  • 単体: MAVLink ルータ、コマンドポリシー、DataFlash パーサ(実ログのフィクスチャ)、解析ルール。
  • 統合: ArduPilot SITL を docker で N 台(Copter 4 + Rover 2)起動し、接続・モード変更・Guided・パラメータ往復・リンク喪失を自動化。
  • UI: Playwright で 10 画面の遷移とオフライン(ネットワーク遮断)時の地図表示を検証。
  • 負荷: 30 機 × 50 Hz テレメトリ + 6 映像で CPU/メモリ/IPC レイテンシを計測し、UI 更新 10 Hz を維持できることを確認。

10. 実装ロードマップ

  1. M1 コア接続(4 週): rgcs-core / rgcs-mavlink / 運用 2D マップ / 機体リスト / 全コマンド / 操作履歴。SITL 2 機で動作。
  2. M2 多機体・映像(4 週): 20 機ルーティング、Guided 移動、全機体映像 + 最大化、AUTO REC、オペレータ登録。
  3. M3 メンテナンス(4 週): パラメータ UI、校正、変更履歴、DataFlash 解析 + ルール AI、3D 地図(地形)。
  4. M4 入力・運用品質(3 週): ジョイスティック 2 系統、オフラインタイル管理、i18n 完成、3 OS パッケージング、負荷試験。
  5. M5 AI チャット(3 週): ローカル LLM 統合、ツール呼び出し、ログ Q&A。
